# Журнал замеров и грабли

Всё, что измерено на RTX 5090 (33,7 ГБ по счёту `mem_get_info`) за сессию
18.09.2026. Разброс между прогонами — около ±10%, сравнивать стоит порядок
величины. Обозначения: **G** — время генерации куска, **L** — длительность
куска в эфире, критерий из дизайн-дока — `G/L < 1`, цель 0,5–0,7.

## 1. Выбор модели

### 2B distilled — рабочая

`ltxv-2b-0.9.8-distilled` (6,3 ГБ). Отдельного diffusers-репозитория нет: 0.9.8
лежит в `Lightricks/LTX-Video` одним `.safetensors`, поэтому трансформер и VAE
грузятся через `from_single_file`, а T5, токенизатор и планировщик — из
diffusers-репозиториев.

Цепочка из 30 кусков, 704×480, 97 кадров, 8 шагов, перекрытие 9:

| | |
|---|---|
| G, медиана | 1,83 с (мин 1,81, макс 2,70) |
| G/L, медиана | **0,50** (худший кусок 0,74) |
| кусков с G/L ≥ 1 | 0 % |
| пик VRAM | 19,3 ГБ (9,7 ГБ с выгруженным T5) |

Первый кусок всегда ~3,8 с — прогрев, в эфире покрывается буфером.

### 13B distilled — проверена и отклонена

Наивно не запускается: трансформер 26 ГБ + T5-XXL 9,5 ГБ + VAE 2,5 ГБ ≈ 38 ГБ
против 33,7. Оперативной памяти 30 ГБ, поэтому собрать пайплайн на CPU и
перенести на карту тоже нельзя.

Рабочая схема: T5 поднимаем только на CPU, кодируем промпты, выгружаем; трансформер
грузим сразу в видеопамять через `device_map="cuda"`; пайплайн собираем с
`text_encoder=None`. Плюс `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` и
тайлинг VAE.

| конфигурация | bf16 | fp8 | fp8 + compile |
|---|---|---|---|
| 704×480 | 7,05 с / 1,75 | 6,25 с / 1,55 | **4,79 с / 1,19** |
| 768×512 | 8,65 с / 2,14 | 7,90 с / 1,95 | — |
| 640×384 | — | — | **2,76 с / 0,68** |
| 576×352 | — | — | **2,26 с / 0,56** |
| 512×320 | 2,94 с / 0,73 | 2,81 с / 0,69 | **1,84 с / 0,46** |
| пик VRAM | 30–31 ГБ | **17–18 ГБ** | **17–18 ГБ** |

Очная ставка на равных, один сид и промпт: 13B fp8+compile @640×384 даёт
G/L 0,68–0,77, а 2B bf16 @704×480 — 0,46–0,51, и при этом **выглядит лучше**:
у 13B на низком разрешении смазывается лицо. Преимущество большой модели не
доживает до разрешения, которое она может себе позволить по скорости.

### fp8 и torch.compile

Готовый `ltxv-13b-0.9.8-distilled-fp8.safetensors` **для diffusers не годится**:
в заголовке 480 тензоров `F8_E4M3` и ни одного масштабного коэффициента
(`scale_shift_table` — это параметр AdaLN, не квантование).

Квантуем сами: `torchao.quantize_(transformer, Float8DynamicActivationFloat8WeightConfig())`
поверх bf16-весов, доли секунды, 26,6 → 14,1 ГБ. `diffusers.TorchAoConfig` не
работает — 0.40 не дружит с torchao 0.18 («Unable to import torchao Tensor objects»).

* **fp8 даёт память, а не скорость:** −50 % весов, всего −10 % времени.
* **`torch.compile` на 2B бесполезен** — разница в пределах шума, на 704×480 даже
  в минус. Его −25 % на 13B компенсировали накладные расходы torchao (квантование-
  деквантование на каждом слое), а не ускоряли модель.
* **Выгрузка T5** после кодирования промпта — бесплатные −10 ГБ VRAM.

## 2. Разрешение

2B, куски по 97 кадров, 8 шагов, T5 выгружен, G/L посчитан для цепочки:

| разрешение | G | G/L в цепочке | пик VRAM |
|---|---|---|---|
| 704×480 | 1,77 с | 0,48 | 9,7 ГБ |
| **768×512** | 2,22 с | **0,61** | 10,2 ГБ |
| 960×544 | 3,21 с | 0,88 | 11,5 ГБ |
| 1152×640 | 5,29 с | 1,44 | 13,6 ГБ |

Прирост детализации виден глазами: на 704×480 колки грифа смазаны, на 960×544
читается логотип. Упираемся во время, а не в память — 20 ГБ VRAM девать некуда.

## 3. Стыки и деградация цепочки

На 110 секундах (30 кусков) всё выглядело хорошо, и это оказалось обманчиво:

* **Стыки проблемы не представляют.** Межкадровая разница на границах кусков
  7,52 против фоновых 8,50 (×0,88) — стыки спокойнее обычного кадра, потому что
  кусок начинается с латентов хвоста. Кроссфейд не нужен, 9 кадров перекрытия хватает.
* **Расплывания картинки нет.** Кадр на 109-й секунде такой же резкий, как на первой.
* **Но сцена монотонно уползает:** камера наезжает до крупного плана, героиня
  перестаёт узнаваться, снос средней яркости 16,8/255.

**Шаг 0 мерил 110 секунд — этого достаточно для скорости и стыков, но слишком
мало, чтобы увидеть коллапс.** На дистанции в 4–5 минут картина другая (раздел 4).

## 4. Дрейф сцены: девять проверенных подходов

Главный отрицательный результат сессии. Похожесть последнего кадра куска на
исходник (корреляция гистограмм HSV) падает с 0,85 до 0,24 за 12 кусков.

| подход | результат |
|---|---|
| промпт про статичную камеру | убирает штатив из кадра, дрейф остаётся |
| стабилизация на выходе (OpenCV) | **замерено:** dx −229 → −238 px, не работает |
| замкнутая геометрическая коррекция | не работает: дрейф **смысловой**, не геометрический |
| окно условия ×4 (перекрытие 9 → 33) | **замерено:** 0,24 → 0,27, то есть не влияет; −54 % скорости |
| якорь к исходнику раз в 3 / 15 / 30 кусков | двигает точку между «уплывает» и «петля» |
| длинный пайплайн, батчи по 20 с | внутри батча держит отлично, между батчами копится |
| нормализация цвета по опорному кадру | лечит симптом: кислота уходит, фактура всё равно разваливается |
| якорь идентичности (`negative_index_latents`) | не работает |
| **без обратной связи** | **стабильно бесконечно** |

**Вывод: любая подача сгенерированных кадров обратно в модель разваливается за
~4 минуты.** Это свойство итеративной генерации, а не настройка. Механизм: в
условии всего 2 латентных кадра, идентичности сцены там нет, и модель каждый раз
досочиняет остальное из промпта; артефакты усиливаются на каждом витке.

Почему стабилизация не могла помочь: дрейф — это не дрожание, а настоящий проезд
камеры на 230 px из 704 плюс наезд на 40 % за 25 секунд. Компенсировать это
обрезкой значит выбросить треть кадра и дальше больше.

## 5. Граф ключевых кадров — проверено, работает

`LTXConditionPipeline` принимает условие на **произвольный кадр**, не только на
нулевой (`LTXVideoCondition(image=..., frame_index=N)`). Замер на клипах по 97 кадров:

| режим | \|первый − последний\| | движение между кадрами |
|---|---|---|
| условие только на начало | 37,4 | 4,41 |
| **петля** (один кадр в начале и в конце) | **2,7** | 0,88 |
| **переход A → B** | 21,4 (при \|A−B\| = 20,7) | 4,15 |

Модель **точно приводит клип в заданный конечный кадр**: переход заканчивается
ровно на B, расхождение совпадает с расстоянием между самими кадрами. Петля
смыкается почти идеально.

Оговорка: закреплённые оба конца душат движение — в петле его в пять раз меньше.
Для «дышит и моргает» достаточно, для танца нужны петли подлиннее. Переходы
движение сохраняют полностью.

## 6. Длинный пайплайн: `LTXI2VLongMultiPromptPipeline`

Скользящее временное окно с авторегрессивной сшивкой, жёсткое условие на первый
кадр маской токенов, AdaIN между окнами. Внутри батча сцену держит заметно лучше
цепочки кусков: на 20 секундах кадр остаётся полностью узнаваемым.

Скорость при 576×768: денойз 11,4 с + декод 4,9 с на 20 с видео → **G/L 0,82**.
На коротких батчах выгоднее: 121 кадр (5 с) → 2,3 с + 1,4 с → **G/L 0,73**.

### Грабли API

* `output_type` по умолчанию **`"latent"`** — первый прогон вернул «128 кадров»,
  это оказалось число латентных каналов.
* При `output_type="pt"` возвращается **сырой тензор [B, C, T, H, W] в [-1, 1]**,
  постпроцессор не применяется — он есть только для `np` и `pil`.
* `output_type="np"` тащит 2,5 ГБ float32 через шину: декод «дорожал» с 5,0 до
  9,3 с. Перевод в uint8 **на GPU** решает.
* Конвертация 481 кадра в PIL стоит ~9 с — в эфир кадры должны уходить тензором.
* Декод по умолчанию идёт 16 плитками (4×4) в float32: 4,6 с. Плитки 2×2 дают
  2,9 с, но пик 28,2 ГБ; 1×1 — OOM.
* `negative_index_latents` по умолчанию **приравнивается к `cond_latents`**, то
  есть якорем идентичности служит тот же подпорченный кадр.

## 7. Прочие грабли окружения

* **Ядро ноутбуков — системный python** (`/usr/bin/python3`, torch 2.14+cu130).
  В `/venv/main` другой torch и нет diffusers.
* transformers 5.x не читает T5-токенизатор без `tiktoken` + `sentencepiece`
  (падает с `ValueError: tiktoken is required`).
* `export_to_video` требует `imageio-ffmpeg` либо OpenCV, иначе падает уже после
  успешной генерации.
* `Lightricks/LTX-Video` в diffusers-формате — это **`LTXPipeline`**, text-to-video;
  у неё нет аргумента `image`. Для картинки на входе нужен `LTXImageToVideoPipeline`
  или `LTXConditionPipeline`.
* Distilled работает **без CFG** (`guidance_scale=1.0`), а при этом
  `negative_prompt` даже не кодируется: `do_classifier_free_guidance` — это
  буквально `guidance_scale > 1.0`.
* Ограничения формы: ширина и высота кратны 32, число кадров и длина перекрытия
  вида `8k + 1`.
* `np.stack` на 2650 кадров просит ~11 ГБ при 30 ГБ RAM — метрики по длинным
  роликам считать потоково, иначе OOM-киллер (код 137).
* **`pkill -f` с шаблоном, который встречается в собственной команде, убивает
  сам себя** (наступали дважды, процессы падали с кодом 144). Останавливать
  воркер по `stream/worker.pid`.
