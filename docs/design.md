# StreamingDiffusion — дизайн

## Идея

Одностраничный сайт, на котором идёт бесконечный стрим. Весь видеоряд генерирует
диффузионная видеомодель (LTX-Video) кусок за куском, склеивая их в непрерывное видео.
Зрители пишут в чат, и их запросы влияют на то, что происходит в кадре.

Звука в первой версии нет.

## Ограничения

- Одна GPU: **RTX 5090** (32 ГБ VRAM). Запасной вариант — аренда одной H100.
- Все модели запускаются на своём железе, без внешних API.
- Свой сайт, без Twitch/YouTube.

## Архитектура

Три части:

```
  ┌──────────── Сайт (одна страница) ────────────┐
  │   [ видеоплеер HLS ]       [ чат ]           │
  │   кнопка «Старт/Стоп» (для админа)           │
  └───────▲──────────────────────┬───────────────┘
          │ видео (HLS)           │ сообщения чата (WebSocket)
  ┌───────┴──────────────────────▼───────────────┐
  │  Веб-сервер                                   │
  │  • отдаёт страницу и HLS-сегменты             │
  │  • принимает чат и рассылает его всем         │
  │  • хранит состояние «стрим идёт / не идёт»    │
  └───────▲──────────────────────┬───────────────┘
          │ готовое видео         │ старт/стоп + запросы из чата
  ┌───────┴──────────────────────▼───────────────┐
  │  GPU-воркер (RTX 5090)                        │
  │  бесконечный цикл генерации LTX-Video         │
  │  → ffmpeg → HLS                               │
  └───────────────────────────────────────────────┘
```

Если 5090 стоит дома, веб-сервер можно держать на дешёвом VPS: GPU-воркер сам
отправляет видео на сервер, и открывать порты домашней сети не нужно.

### Сайт

- Одна страница: HLS-плеер (hls.js) и чат.
- Пока стрим не запущен, вместо плеера надпись «офлайн».
- Кнопка «Старт/Стоп» доступна только админу (защищена паролем).
- В чате видно, что запрос принят и когда он попадёт в кадр
  («появится в следующем фрагменте»), а также чей запрос сейчас на экране.

### Веб-сервер

- Отдаёт страницу и HLS-плейлист/сегменты.
- Чат через WebSocket: принимает сообщения, рассылает всем зрителям.
- Передаёт GPU-воркеру команды старт/стоп и очередь запросов из чата.
- Простой фильтр сообщений (длина, стоп-слова, частота).

### GPU-воркер: цикл генерации

```
 1. берём хвост предыдущего куска (последние кадры)
 2. берём промпт: из чата, если есть запрос, иначе «продолжай сцену»
 3. LTX-Video генерирует следующий кусок, ~5 с (121 кадр при 24 fps)
 4. отрезаем кадры-перекрытия, отдаём кусок в ffmpeg → HLS
 5. повторяем
```

Один процесс ffmpeg работает всё время стрима и получает кадры непрерывно, поэтому
в видеопотоке нет разрывов по времени.

## Главная техническая задача: генерация без пауз

Кусок длиной **L** секунд генерируется за **G** секунд. Видео не прерывается, если
**G < L**. Цель — G ≈ 0,5–0,7 × L.

```
показ:      [кусок 1 ........][кусок 2 ........][кусок 3 ........]
генерация:  [ген 2 ....]      [ген 3 ....]      [ген 4 ....]
                        ↑ запас                  ↑ запас
```

- **Буфер:** перед выходом в эфир заранее генерируем 1–2 куска. Буфер покрывает
  случайные замедления.
- **Компромисс:** чем больше буфер, тем надёжнее стрим, но тем медленнее реакция на чат.

### Выбор модели

| Модель | Роль |
|---|---|
| `Lightricks/LTX-Video` `ltxv-2b-0.9.8-distilled` | Стартовая: самая быстрая, «real-time capable» |
| `ltxv-13b-0.9.8-distilled-fp8` | Если у 2B есть запас по скорости: лучше качество, помещается в 32 ГБ |
| LTX-2.x (22B) | Позже; для реального времени на 5090, скорее всего, слишком тяжёлая |

### Ускорение

- Ниже разрешение (768×512 или меньше).
- Distilled-модель с малым числом шагов.
- fp8, `torch.compile`.
- Генерировать 12–15 fps и дорисовывать промежуточные кадры через RIFE до 24–30 fps.
- Конвейер: пока кусок N декодируется и кодируется, уже генерируется N+1.

## Стыки между кусками

| Проблема | Причина | Решение |
|---|---|---|
| Рывок движения на стыке | По одному кадру модель не знает, куда двигалась сцена | Условие на **несколько последних кадров** (продолжение видео в LTX), отрезать перекрытие, при необходимости короткий кроссфейд |
| Картинка «плывёт» со временем | Каждый кусок строится на сгенерированном, ошибки копятся | Периодическая **смена сцены** (новый кусок из текста или «чистой» картинки), коррекция цвета по опорному кадру |
| Резкая смена сюжета из чата | Новый промпт далёк от текущей сцены | Делать намеренную смену сцены с переходом |

**Правило:** спокойное продолжение склеиваем по хвосту; запрос из чата или слишком
долгая сцена — повод для новой сцены.

## Реакция на чат

Промпт подставляется в начале генерации очередного куска, поэтому запрос появится
на экране примерно через **5–15 секунд**.

- Версия 1: сообщение из чата после фильтра напрямую становится промптом.
- Версия 2: маленькая LLM (3–4B, лучше на CPU через llama.cpp, чтобы не отнимать
  GPU у видео) переписывает короткие сообщения зрителей в подробные промпты,
  отсеивает мусор и придумывает продолжение, когда чат молчит.

## Риски

- **RTX 5090 (Blackwell)** требует CUDA 12.8+ и свежий PyTorch; часть библиотек
  придётся собирать или подбирать совместимые версии.
- **Деградация** на длинной дистанции: проверять не 10 секунд, а 10–30 минут.
- **Лицензии моделей:** до коммерческого использования прочитать лицензию LTX-Video.
- **Модерация:** зрители будут пытаться сгенерировать недопустимое — нужен фильтр
  промптов.

## План работ

0. **Бенчмарк на 5090 (без сайта).**
   - Цепочка из 20–30 кусков, каждый склеивается по хвосту предыдущего.
   - Замерить G для каждого куска при 2–3 разрешениях, расход VRAM.
   - Склеить в одно видео и оценить глазами стыки и деградацию к концу.
   - Критерий успеха: G < L с запасом, стыки терпимые.
1. **Цикл и стриминг.** Бесконечная генерация → ffmpeg → HLS → просмотр в браузере.
2. **Сайт.** Страница с плеером, чатом и кнопкой старт/стоп.
3. **Чат → промпты.** Сначала напрямую через фильтр, затем через LLM.
