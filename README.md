# StreamingDiffusion

Бесконечный стрим на одной странице: весь видеоряд генерирует диффузионная
видеомодель (LTX-Video) кусок за куском, зрители пишут в чат и влияют на
происходящее в кадре. Всё крутится на своём железе, без внешних API.

Полный замысел — [docs/design.md](docs/design.md).
Журнал замеров и разобранные грабли — [docs/findings.md](docs/findings.md).

## Быстрый старт

```bash
cd stream
# ядро — системный python (см. «Окружение»), не /venv/main
/usr/bin/python3 build_pool.py                 # ~65 с, собирает 60 опорных кадров
/usr/bin/python3 worker_long.py \
    --feedback 0 --pool-dir pool --frames 121 --crossfade 12 \
    --prompt "Webcam stream of a young woman gamer with headphones at her desk, ..."
```

Воркер поднимает и генерацию, и ffmpeg, и http-сервер со страницей плеера на
`127.0.0.1:17070`. Снаружи — через Caddy на порту `10100`:

```
http://$PUBLIC_IPADDR:$VAST_TCP_PORT_10100/?token=$OPEN_BUTTON_TOKEN
```

Останавливать **строго по pid-файлу**: `kill $(cat stream/worker.pid)`.
Не использовать `pkill -f` — шаблон совпадёт с командной строкой собственной
оболочки, и команда убьёт сама себя (наступали дважды).

## Что где лежит

| файл | назначение |
|---|---|
| `stream/worker_long.py` | рабочий воркер: генерация → ffmpeg → HLS + http + чат-канал |
| `stream/build_pool.py` | сборка пула опорных кадров (12 вариантов × 5 кадров) |
| `stream/worker.py` | ранняя версия на цепочке кусков; оставлена для сравнения, деградирует |
| `stream/hls/index.html` | страница: плеер hls.js, живая статистика, поле промпта |
| `stream/pool/` | опорные кадры (генерируются, в git не попадают) |
| `test_LTXV.ipynb` | инференс 2B, цепочка кусков, замеры G/L |
| `test_LTXV_13B.ipynb` | 13B: память, fp8 через torchao, `torch.compile` |

## Как устроен эфир

```
пул опорных кадров ──> дубль 5 с (LTXI2VLongMultiPromptPipeline)
                           │
                           ├─ кроссфейд 12 кадров на стыке
                           ▼
                   очередь (буфер 2) ──> ffmpeg -re ──> HLS ──> hls.js
                                              ▲
                                   обратное давление: -re
```

Ключевое решение: **выход модели не возвращается ей на вход**. Каждый дубль
стартует со случайного кадра из замороженного пула, поэтому деградация не
накапливается. Флаг `-re` заставляет ffmpeg читать stdin в реальном времени —
это и есть обратное давление, из-за которого генератор не убегает вперёд.

Текущие показатели: **G/L ≈ 0,73** при 576×768, пик VRAM ~16 ГБ из 33,
простоев нет, задержка реакции на чат 5–10 с.

## Окружение

Ядро и пакеты — **системный python** `/usr/bin/python3` (torch 2.14+cu130).
В `/venv/main` лежит другой torch и нет diffusers; ядро туда не переключать.

```bash
/usr/bin/python3 -m pip install -U diffusers transformers accelerate \
    tiktoken sentencepiece protobuf imageio imageio-ffmpeg \
    opencv-python-headless torchao
```

Веса кэшируются в `$HF_HOME` = `/workspace/.hf_home` (~70 ГБ). Токен HF не нужен.

## Что дальше

Главное ограничение установлено экспериментально: **любая подача сгенерированных
кадров обратно в модель разваливается за ~4 минуты** — девять проверенных
подходов в [docs/findings.md](docs/findings.md). Поэтому бесконечная генерация
«вперёд» невозможна, и текущий эфир держится только на отсутствии обратной связи.

Проверенный выход — **граф ключевых кадров**: просить модель не о бесконечности,
а о клипе между двумя известными позами. Замерено, что она приводит клип в
заданный конечный кадр точно (расхождение 2,7 из 255 для петли). Из этого
строится граф состояний «сидит → встаёт → танцует → садится» без дрейфа по
построению. Подробности — в [docs/design.md](docs/design.md), раздел
«Граф ключевых кадров».
